# 레이어별 TDD/BDD 구현

저장소 AGENTS.md를 먼저 읽는다. 작업 범위와 5분 제한을 지킨다.

## 배치와 의존성

- ui: 화면·표현·사용자 입력. 도메인 계산이나 저장소 접근을 넣지 않는다.
- app: 유스케이스와 실행 흐름 조정. 외부 기술은 필요한 경계로 분리한다.
- domain: 계산·규칙·모델. UI 프레임워크나 DB 클라이언트를 참조하지 않는다.
- infra: DB·네트워크·파일·외부 서비스 어댑터.
- 프로그램과 테스트 모듈 모두 해당 레이어 디렉터리에 둔다. 스킬의 실행 코드는 scripts/app, scripts/domain, scripts/infra 같은 구조를 사용한다.
- 기존 구조를 먼저 확인한다. 전체 디렉터리를 요청 없이 재배치하지 않는다. 도메인에서 외부 구현을 직접 참조하지 않도록 경계를 둔다.

## Red → Green → Refactor

1. 요구 동작을 Given/When/Then 또는 입력·기대 결과로 정한다.
2. 동작을 검증하는 최소 단위 테스트를 먼저 작성하고 실행해 실패를 확인한다. 구현 누락으로 시작하는 경우 모듈 부재 실패를 확인한 뒤 구현한다.
3. 요구를 충족하는 최소 구현을 추가하고 동일 테스트를 통과시킨다. 실제 동작 수정에서는 잘못된 결과를 재현하는 실패 테스트를 우선한다.
4. 중복과 책임을 정리하고 관련 단위 테스트를 다시 실행한다. 외부 의존성은 단위 테스트에서 분리한다.
5. 80줄 경계·레이어 검증을 실행한다. 기능 변경에 필요한 통합 검증은 별도로 수행한다.

## 설계 기준

- YAGNI: 현재 요구에 없는 기능·추상화를 추가하지 않는다.
- KISS: 이해 가능한 작은 함수와 단순한 흐름을 우선한다.
- SOLID: 한 모듈에 한 책임을 두고 변경되는 외부 의존성을 경계에서 처리한다.
- DRY: 같은 지식이 실제 반복될 때 공통화한다. 80줄을 맞추기 위한 압축·세미콜론 병합을 하지 않는다.
- 모든 프로그램·테스트 모듈을 빈 줄·주석 포함 80줄 이하로 유지한다. 책임별로 나누되 불필요한 패턴은 도입하지 않는다.

검증에는 저장소 `.agents/skills/yogurt-module-check/SKILL.md`의 명령을 사용한다. 스크립트 통과는 TDD 수행이나 설계 적합성을 증명하지 않는다. 실패→통과 기록과 설계 판단도 확인한다.
